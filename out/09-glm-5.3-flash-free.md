# Review of `in/design-document-v1.md` — reviewer 09 (glm-5.3-flash-free)

## Summary

A well-structured draft for a portable, rules-governed workspace with a small CLI secret manager. The core ideas — key paths, native-store-first backends, a single plaintext export — are reasonable, but the document contradicts itself on where values may live, and the portability goal is asserted rather than specified.

## Strengths

- **Section 4's inventory discipline is the strongest part.** Per-row `status` values (§4), the "records the decision, not the installation" stance (§4.4), and the alias/full-model/provider/key-path quadruple (§4.3) give a precise, low-noise map.
- **The key-path scheme (§5.1) is genuinely good:** collision-free scopes, a stable name reusable as a Credential Manager target, and extensibility without schema changes.
- **CLI hygiene (§5.4):** `set` reads from stdin to keep values out of shell history and `ps`; defined exit codes; `list` is names-only.
- **Honest current state (§8).** Listing the mode-`664` `~/github_token` and the DeepSeek placeholder is exactly what a reviewable design should do.
- **Open questions (§12) are real questions**, not decoration — Q5 (SSH/GPG scope) and Q6 (export cadence) are the right ones to ask.

## Weaknesses

1. **Internal contradiction on "where values live."** §5.3 declares `~/SECRETS` "the only file that ever contains values", yet §5.5 step 5 creates `secrets-import.txt` with `KEY_PATH = value` lines in plaintext, and §5.2's fallback is an "export file" that may persist per §6 ("exports must be taken periodically"). Three plaintext artifact classes, one rule.

2. **§5.5 step 5 breaks the §5.3 format.** The import helper writes `=`-separated lines while the defined export format is `|`-separated and parsed by "split on the first `|`" (§5.3). The tool would need a second parser its own spec doesn't define.

3. **Export as backup vs. export as temp file are unreconciled.** §5.2 says the export "is deleted after import"; §6 makes it the "backup of last resort" taken periodically — which contradicts deletion and leaves location, retention, and rotation undefined (§12.6 punts to an open question instead of deciding).

4. **No archival specification.** §6 step 1 is "archive the folder" with no format, no exclusion list beyond `.tmp/`, no checksum, and no verification step beyond `secret.py list`. The success criterion (§1) is untestable as written.

5. **Multi-backend breadth is over-engineered for the stated estate.** §4.1 lists two machines (Q4OS, Windows 10), yet §5.2 specifies five backends including macOS Keychain — an OS that appears nowhere in the inventory. For 7 secrets (§8), a two-backend design (KWallet + file) would meet every goal.

6. **DCOP first-bind risk.** Even §10 admits KWallet's DCOP interface is undocumented and may block requiring GUI; yet the roadmap (§9) makes the KWallet backend a phase-2 requirement while `secrets-import.txt` (§5.5) is the de facto primary on `q4os` until phase 0 finishes. The design leans on its weakest pillar.

## Gaps

- No README.md exists (§3, §8) despite being the designated entry point (§2, rule 3).
- No threat model for the agent itself: `secret.py get` prints the value to stdout (§5.4); an AI assistant that runs it puts the value into session context and session history — stored on disk per §6 exclusions. §5.6's "values never chain against the agent" clause ("No network access", "does not decide policy") does not cover this.
- No mention of how the `in/`/`out/` review artifacts (§3) interact with rule 3's archive rule — they may contain stray machine-specific paths.
- No test scope defined; `tests/` is only "planned" (§3), yet §6 step 6 makes "tests pass" a recovery-verification step.
- No policy for fixing the known `~/github_token` mode-664 issue (§8) — acknowledged but unowned.
- Model table gaps in §4.3: no timestamp/retirement tracking for the "free" alias (risk §10 admits free models expire, but the table has no status column), and `deepseek-chat` lacks the provider-prefixed form every other row has.

## Recommendations (priority order)

1. Merge AGENTS.md / MODELS.md / KEYS into INVENTORY.md now (§3, §8); three overlapping "truths" violate rule 3's portability test immediately.
2. Fix the §5.5/§5.3 format contradiction: use the `|` format for `secrets-import.txt` too, and state explicitly which plaintext artifacts are legitimate and their lifetimes ("export as backup" needs a location and schedule).
3. Capsule the archival procedure: exact command, exclusion list, checksum, verification steps appended to §6.
4. Add an agent-facing security rule: values may be injected into environment/tools, never shown in conversation; audit `get`'s stdout path.
5. Cut the backend matrix to `auto, file, kwallet, wcm` (§5.4); add macOS only when a Mac appears in §4.1.
6. Add a `status` column to §4.3 and fix the deepseek row's form.

## Answers to the six questions

1. **Internally consistent?** Mostly, but not fully: §5.3 vs §5.5 (format), §5.2 vs §6 (export lifetime) contradict each other.
2. **Missing for portability?** The archival procedure itself — format, exclusions, checksum, verification — is unspecified, and README.md doesn't exist yet.
3. **Over-engineered?** The five-backend CLI and multi-level work scopes for two machines and seven secrets.
4. **Unaddressed security risk?** Secret values leaking through agent session context via `get` on stdout; no injection/no-display rule exists.
5. **Change first?** Consolidate the three inventory files and reconcile the export-file rules (recommendations 1–2).
6. **Is the secret-manager design sound?** The scheme is sound: key paths are a good idea, native-store-first is right, stdin-only `set` and exit codes are solid. Weak points: DCOP/KWallet reliance, plaintext export ambiguity, and the parsing contradiction of §5.5.

## Verdict

**6** — A solid, honest skeleton with a genuinely good naming scheme, undermined by self-contradictions in the secret-lifecycle rules and an unpacked portability procedure.
