# План за `secret.py` — инструмент за тайни

Статус: **чака одобрение**. Нищо не е изпълнено.

## 1. Цел

Един инструмент, който пази тайните по един и същ начин на всяка машина:

- основно хранилище — native store: KWallet (Q4OS/TDE), GNOME Keyring (Mint),
  Windows Credential Manager, macOS Keychain;
- `~/SECRETS` — **временен експорт**, не постоянно хранилище: създава се само при
  пренос на друга машина, резервно копие или машина без работещ keyring;
- имената на тайните са **пътища**, еднакви навсякъде.

Инструментът не е сървър и не пази нищо сам — той само чете и пише в избран
backend.

## 2. Схема на имената

```
доставчик / обхват / вид
```

Примери:

```
github/personal/token
github/work/prj1/token
github/work/prj2/token
nvidia/personal/api_key
gemini/personal/api_key
```

- първи сегмент — доставчик;
- последен — вид (`token`, `api_key`, `password`, `secret`);
- между тях — обхват, колкото нива са нужни.

Правила за валидност: само `a-z`, `0-9`, `-`, `_` и `/`; без начален `/`, без `..`,
без интервали; минимум два сегмента.

Съответствие с WCM:

| Наше | WCM |
|---|---|
| `KEY_PATH` | target name |
| `value` | secret |

## 3. Файлове

```
tools/secret.py              # CLI + двата backend-а (един файл, само stdlib)
tools/secret_probe.py        # еднократна проверка на KWallet (само четене/тест)
tests/test_paths.py          # валидация на пътища
tests/test_file_backend.py   # файлов backend
tests/test_kwallet_backend.py# DCOP backend с mock
tests/test_cli.py            # CLI през subprocess
tests/fixtures/              # примерни файлове, без истински тайни
```

Един файл за инструмента — без пакети и без външни зависимости.

## 4. CLI

```
secret.py get  <path>                 # само стойността, за скриптове
secret.py set  <path> [--stdin]       # стойност от stdin или интерактивно
secret.py del  <path>
secret.py list [--json]               # само имена, никога стойности
secret.py export --out -              # към stdout (за прехвърляне)
secret.py import --in -               # от stdin
secret.py probe                       # проверка на KWallet
```

Общи опции:

- `--backend {auto,file,kwallet}` — по подразбиране `auto`;
- `--file PATH` — по подразбиране `~/SECRETS`;
- `--quiet`.

`auto` означава: ако KWallet е достъпен и отключен — KWallet, иначе файл.

Изходни кодове:

| Код | Значение |
|---|---|
| 0 | успех |
| 1 | няма такъв ключ |
| 2 | грешка в backend-а |
| 3 | грешка в аргументите |

Сигурност:

- `set` чете стойността от stdin, **не** от аргументите (за да не влиза в историята
  на shell-а и в `ps`);
- `list` и `probe` никога не печатат стойности;
- файлът се записва атомарно (временен файл в същата папка, `chmod 600`,
  `os.replace`);
- при грешка не се оставя частично записан файл.

## 5. Формат на експорта `~/SECRETS` (mockup)

`~/SECRETS` е временен файл за пренос, не постоянно хранилище. Избран формат —
**две колони, разделител `|`**, един ред на тайна:

```
# KEY_PATH | value
github/personal/token | ghp_...
github/work/prj1/token | ghp_...
nvidia/personal/api_key | nvapi-...
```

Защо този:

- работи и от shell (`grep`, `cut`), и от Python;
- четим е с очи;
- `|` практически не се среща в токени;
- разделя се само по **първия** `|`, така че стойност с `|` не чупи реда;
- празните редове и редовете с `#` се игнорират;
- дублиран път е грешка, не „последният печели“.

Алтернативи, които отхвърлям: JSON (неудобен за ръчна редакция), TOML (излишна
структура), dotenv `KEY=value` (стойностите често съдържат `=`).

За тестовете има и **in-memory mockup** — `dict` backend, който не пипа диска.

След успешно импортиране в keyring-а експортът се изтрива.

## 6. KWallet — как ще го проверим

Първо **probe**, без истински тайни:

1. има ли `dcop` и `kwalletd`; работи ли услугата;
2. `dcop` — списък на услугите и интерфейсите;
3. има ли отворен портфейл (`isOpen`), иска ли парола;
4. запис/четене/изтриване на тестов ключ `test/probe/value`;
5. ако има `kwalletcli` — проверява се и него.

Очакван резултат: или работещ backend, или ясно „не става за автоматизация“
(заключен портфейл, иска GUI). Тогава файлът остава основен, а KWallet —
само ръчен/огледален.

Важно: probe-ът не пипа `~/SECRETS` и не записва истински стойности.

## 7. Тестове

`unittest`, стандартна библиотека, без мрежа.

**Пътища:** валидни/невалидни, `..`, начален `/`, интервали, един сегмент, дълги
имена.

**Файлов backend:** запис → четене → изтриване; права `600`; атомарност;
коментари и празни редове; дублиран ключ; стойност с `|`; липсващ файл; файл без
права.

**CLI:** `set` през stdin, `get` връща само стойността, `list` не показва
стойности, код 1 за липсващ ключ, код 3 за лош аргумент, `--file` сочи temp
директория.

**KWallet backend:** с fake `dcop` (mock на `subprocess`) се проверява само
изграждането на командите и разборът на отговора; реален тест само ако портфейлът
е отключен, иначе `skipUnless`.

**Сигурност:** след `set` файлът е `600`; `list`/`probe` не съдържат стойности в
изхода.

## 8. Миграция

0. събиране на всички тайни на машината на едно място (виж раздел 8а);
1. сегашните 7 ключа се преименуват на пътища:
   `GITHUB_TOKEN` → `github/personal/token`, `NVIDIA_API_KEY` →
   `nvidia/personal/api_key` и т.н.;
2. `secret.py import` от стария файл във новия формат;
3. проверка: `list` дава същите 7 пътя, `get` връща същите стойности;
4. `KEYS` се изтрива, съдържанието му отива в `INVENTORY.md`;
5. `[models]` се маха от `~/SECRETS` — там остават само тайни;
6. `MODELS.md` и `INVENTORY.md` сочат пълния `KEY_PATH`;
7. правило 3.9 в `AGENTS.md` се обновява;
8. комит `v2 - inventory`.

## 8а. Събиране на тайните на машината

Преди миграцията се прави пълен списък на местата, където на тази машина има тайни.
Известни кандидати:

| Източник | Какво може да има | Статус |
|---|---|---|
| `~/github_token` | личен GitHub токен | потвърден |
| `~/confg-kiko.yaml` | 8 модела с API ключове | потвърден |
| `~/Documents/confg-kiko.yaml` | копие на същия файл | за проверка |
| `~/Documents/config-kiko.yaml` | повреден/двоичен файл | за проверка |
| `~/.kiko/kiko.db` | база на kiko-proxy, възможно ключове | за проверка |
| env `ANTHROPIC_AUTH_TOKEN` | токен в средата | потвърден |
| `~/.configtde/opencode/opencode.jsonc` | конфигурация (празна) | проверен |
| `~/.ssh/`, `~/.gnupg/` | ключове за достъп | за решение |

Правила:

- всяка намерена тайна получава път по схемата;
- еднаквите стойности се сливат в един ключ;
- нищо не се копира в проекта;
- накрая списъкът се сверява: всеки източник е или включен, или изрично отбелязан
  като „не е тайна“.

## 9. Фази

| Фаза | Какво | Резултат |
|---|---|---|
| 0 | probe на KWallet | решение кой backend е основен |
| 0.5 | събиране на тайните на машината | списък с всички източници |
| 1 | пътища + файлов backend + CLI + тестове | работещ инструмент без KWallet |
| 2 | KWallet backend + mock тестове | втори backend, ако probe-ът е успешен |
| 3 | миграция + `INVENTORY.md` | нов ред в проекта |
| 4 | документация + комит | завършено |

Фаза 1 не зависи от фаза 0 и може да се направи веднага.

## 10. Рискове

- **Заключен KWallet** — DCOP заявката може да блокира или да иска GUI. Затова
  probe-ът е с таймаут (3 секунди) и при провал се връща на файл.
- **DCOP интерфейсът не е документиран** — имената на методите се откриват с
  `dcop <service>`; затова probe-ът е отделна стъпка.
- **Стойност с `|`** — разделя се само по първия разделител; тества се изрично.
- **Дублиране на източници** — файлът е основен; KWallet е огледало, не втори
  източник на истина.

## 12. Критерии за готовност

- `secret.py` работи с файл без допълнителни зависимости.
- Всички тестове минават с `python3 -m unittest discover tests`.
- `list` не показва нито една стойност.
- Файлът е `600` след всяка операция.
- Миграцията не губи нито един от 7-те ключа.
- `~/SECRETS` може да се изтрие след импортиране, без загуба на достъп.
- `INVENTORY.md`, `MODELS.md` и `AGENTS.md` са в съответствие с новата схема.
